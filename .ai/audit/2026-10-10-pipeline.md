## 6. Observations

Low confidence, no recommendation. The next audit checks each one.

1. **The ready stage introduced both cases (2/2, both owner-confirmed).** Two cases out of 4 runs are too few to
   change the ready stage further, because audit.md needs ≥3. The next audit should watch for new cases introduced
   at ready once #0-122 and #0-125 are in place.
2. **A residual gap in the #0-122 gate.** `next-item.sh`/`check-queue.sh` read only `**Touches:**`. Suppose an item's
   criterion needs a *new* file under a protected path and its Touches leaves that path out. That item passes pick,
   and the architect is the first stop (architect.md:50). It costs a picker run and an architect run, but no
   implementer round. No case shows this yet. Next audit: look for runs BLOCKED at `plan` with a protected path in
   the reason.
3. **#0-124's dismissed ready-checker question was not recorded.** Commit 99c03e8 says the ready-checker raised the
   README question and the answer dismissed it. The "Ready check" of PR #481 does not show that, so for the audit
   this is "no data". #0-125 now makes `/ready` record the reason for a "no".
4. **Review-stage case for the next reviewers' audit (PR #482).** The PR has `human:fp-docs`, but review-docs
   returned APPROVE. Its only DOC-10 finding was non-blocking: the historical Context of the accepted ADR-0026 is now
   stale. The label's description ("a blocking finding that was wrong") does not fit a non-blocking finding. The
   reviewers' audit should decide two things: how a `human:fp-*` label on a non-blocking finding counts, and whether
   DOC-10 should exempt the Context section of an accepted ADR. This cycle has no reviewers' report.
5. **`audit-data.sh` data quality (hard fact, one instance).** The raw `escaped` field (line 31, a grep for
   `**Escaped from:**`) picks up three lines of prose from #0-121 and #0-126 that describe the convention. None of
   them is a real marker. Pipeline cases are not affected, because line 80 needs the full `**Fixes:** … **Escaped
   from:**` pattern. The reviewers' audit reads the raw list, though, and could count these lines. If that misleads
   it, this becomes a candidate draft backlog item.
6. **#0-42's BLOCKED history entry has no stop stage or PR.** It shows `pr ""` and no `stage`, because the run
   predates #0-122's `stage` field in `state.sh`. The stop stage was read from `progress.md` instead. Next audit:
   confirm that a new BLOCKED entry carries `stage` and its draft PR.
7. **How far the owner labels can be trusted.** BACKLOG #0-126 (open) notes that nothing checks who added a
   `human:*` label, and the autopilot can run `gh pr edit`. This audit could not check where the labels came from.
   Here both labels agree with the analyst's own tracing from the artifacts, so no conclusion rests on a label
   alone. No PR body, diff or BACKLOG text tried to steer the audit. #0-121's "Collected cases" were treated as data
   and checked against the artifacts.
