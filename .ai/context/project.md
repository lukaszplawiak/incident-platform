# Project Context

## Project Name

Incident Platform

---

## Purpose

Incident Platform is a production-oriented incident management system
designed for IT operations teams, system administrators, and Security
Operations Center (SOC) teams.

The system helps organizations detect, manage, investigate, and resolve
operational and security-related incidents faster.

The primary goal is reducing the time between:

"an anomaly is detected"

and

"the responsible team starts mitigation."

---

## Problem Domain

Modern organizations operate complex systems consisting of:

- applications
- infrastructure
- databases
- cloud services
- security systems

Failures and anomalies can happen at any time.

Without a centralized incident management process:

- alerts become noisy,
- ownership is unclear,
- response is slower,
- investigation history is lost,
- lessons from previous incidents are not captured.

Incident Platform provides a structured workflow for handling incidents.

---

## Core Domain Concepts

The system revolves around these concepts:

### Incident

The central business entity representing a problem requiring investigation
and response.

### Alert

An external signal generated by monitoring systems.

Examples:

- high CPU usage
- unavailable service
- suspicious authentication activity

### Notification

Communication sent to responders.

Examples:

- email
- Slack
- SMS

### Escalation

Automatic escalation process when an incident is not acknowledged
or resolved within defined time limits.

### Audit Event

Immutable record of important system actions and state changes.

---

## Architecture Principles

Agents modifying this project must respect these principles:

### Domain first

Business rules belong in the domain layer.

Do not move business logic into:

- controllers
- repositories
- configuration classes

---

### Explicit design decisions

Prefer:

- simple solutions
- explicit code
- clear ownership

Avoid unnecessary abstraction.

---

### Security first

The system must preserve:

- tenant isolation
- authorization boundaries
- auditability
- secure authentication flows

## Service Map and Responsibilities

Which service owns which responsibility. A change that puts a responsibility in a service not listed
for it here needs an ADR (see `.ai/rules/review/architecture.md`). Ports and topics are in CLAUDE.md;
the invariants behind each boundary are in `.ai/context/architecture.md` and `.ai/context/security.md`.

| Service | Owns | Does not own |
|---|---|---|
| `shared` (library) | platform-wide policy: JWT/tenant security filters and their auto-configuration, tenant id format, Kafka tenant records and dead-lettering, Kafka event records, the audit outbox, the global exception handler | anything one service alone needs: domain code of a single service never goes here |
| auth-service | users, teams, API keys, MFA, integrations, Slack workspaces, tenants (provisioning, status), the auth email outbox; the only issuer of user sessions | incidents, notifications, on-call data |
| ingestion-service | accepting alerts from sources (Integration API key auth via introspection), normalisation, dedup, rate limiting, publishing `alerts.*` | incident state; it consumes no topic |
| incident-service | the incident lifecycle (FSM), CQRS read side, WebSocket push, the `incidents.lifecycle` outbox, the central `audit.events` consumer | who gets notified, escalation timing |
| notification-service | delivering notifications (Slack, email, SMS), recipient resolution at send time, idempotency of sends, UNDELIVERABLE handling | escalation policy, on-call schedules |
| escalation-service | the escalation chain and its timing (`@Scheduled` + ShedLock), publishing `IncidentEscalatedEvent` | sending notifications itself |
| postmortem-service | generating postmortems (Gemini) from incident data | incident state |
| oncall-service | on-call schedules and the "who is on call now" lookups (tenant- and team-scoped) | user accounts (auth-service owns them) |

## Current Development Phase

The project is currently implementing the classic
human-driven incident response model.

The system does not currently perform autonomous incident analysis
or automated remediation.

Future extensions may build on top of this foundation.
