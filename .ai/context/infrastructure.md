## CI gotchas

`.github/workflows/ci.yml` runs build+test (skipped, like the smoke test, on a pull request that changes only
Markdown, at the job so a required check still passes; always on a push to `main`; nothing the build, its tests
or its check scripts read is Markdown, so a new check that reads one must change the `code` filter in
`detect-changes`), a path-filtered Docker image matrix, Kustomize+kubeconform validation of base and all three overlays, a docker-compose smoke test that boots Postgres/Redis/Kafka, the log pipeline (docker-socket-proxy, Loki, Alloy) plus all 7 services and curls each health endpoint (then checks the services' DB role, backlog #0-78, and that every service's lines reach Loki parsed and `docker-socket-proxy` refuses writes on an internal network, `.github/scripts/test-log-collection.sh`, #0-94 step 2, whose `curlimages/curl`/`alpine` tags live only in that script; `docker-compose.yml` requires `DB_PASSWORD`, `POSTGRES_ADMIN_PASSWORD` and `GRAFANA_ADMIN_PASSWORD`, so the job sets them in its job-level `env` — every compose command, teardown included, interpolates them), `postgres-roles` (`.github/scripts/test-postgres-roles.sh`: the Postgres init script and `docs/database-roles-migrate.sql` against the image named in `docker-compose.yml`; plus `.github/scripts/check-db-password-config.rb` and its bypass test `test-db-password-config.sh`: every committed `spring.datasource.password` is exactly `${DB_PASSWORD}`, no literal or defaulted datasource/Flyway password, backlog #0-66), and `validate-monitoring-config` (backlog #0-16): `promtool check config` + `promtool test rules docker/prometheus.rules.test.yml`, `amtool check-config` + `amtool config routes test` assertions on `docker/alertmanager.yml` (Watchdog reaches only the dead man's switch, critical platform alerts reach both operator email and the webhook), and `loki -verify-config` + `alloy validate` + `alloy fmt` (canonical form required) on `docker/loki.yml` and `docker/alloy/config.alloy`. The smoke test never starts Prometheus/Alertmanager, so this job is the only check of that config. It runs the `prom/prometheus` / `prom/alertmanager` images pinned by tag in the job itself, and those tags must equal the ones in `docker/docker-compose.yml` — bump both together (the `grafana/loki` / `grafana/alloy` tags it reads from the compose file itself, #0-94 step 2), or CI validates against a different version than compose runs. A change to a route or receiver in `alertmanager.yml` usually needs a matching `routes test` line in the job. Six structural rules it enforces:

- Every directory with a `Dockerfile` must have a matching Deployment in `k8s/base` (name-matched in the rendered manifest).
- A new runnable service must parent to `service-parent`, not the root POM — that's where `spring-boot-maven-plugin` is declared, and without it `java -jar app.jar` fails with "no main manifest attribute". `shared` deliberately stays on the root parent.
- Mail in k8s (backlog #0-42, ADR-0026, `.github/scripts/check-k8s-mail.rb`): only the dev overlay has Mailpit (ClusterIP, never exposed) and the `SPRING_MAIL_PROPERTIES_*` overrides; the Mailpit image tag must equal `docker/docker-compose.yml`'s (bump both); the dev JVM patches must keep `labelSelector: app.kubernetes.io/component=backend`, and a new infrastructure Deployment in dev needs another component value.
- The rendered staging and prod k8s overlays set no Spring profile, in any form (backlog #0-63): only `k8s/overlays/dev` sets `SPRING_PROFILES_ACTIVE`, because the dev profile enables incident-service's unauthenticated `/dev/token`. A real prod profile would need that check changed on purpose.

The fourth (backlog #0-81): no Spring profile configuration, and no literal secret, is committed under `src/main/resources`: it would ship in every jar and image. "Build, Test & Coverage" runs `.github/scripts/check-packaged-profiles.sh` (after its own cases, `test-packaged-profiles.sh`), which fails on a committed `application-<profile>.*` there, a base `application.*` with a `spring.config.activate.on-profile` key or a `spring.profiles.active` / `include` / `default` / `group`, or a key ending in `secret`, `encryption-key`, `private-key` or `api-key` (any case, kebab or camelCase) that is not a `${VAR}` without default. It has no allow-list: a profile in a jar needs a backlog decision and a change to the script. Test configuration goes in `src/test/resources` or `@TestPropertySource`; deployed configuration comes from the environment; the developer's `application-local.yml` stays gitignored.

The fifth (backlog #0-82): every directory with a `Dockerfile` except `auth-service` sets `auth-service.base-url` from `${AUTH_SERVICE_URL}` in its `application.yml`, or the service silently gives every tenant full access, suspended or not. "Build, Test & Coverage" runs `.github/scripts/check-tenant-status-config.sh` (after its own cases, `test-tenant-status-config.sh`).

Every workflow under `.github/workflows/` declares its own `permissions:` at workflow level (`contents: read`; backlog #0-59) instead of relying on the repository's "Workflow permissions" setting. A job that needs more declares its own block, which replaces the workflow's, so it repeats `contents: read`. A job that runs a PR's own code never gets a write scope. No check enforces this — review does.

Every `uses:` is pinned to a full commit SHA with its tag in a comment (`owner/action@<sha> # vX.Y.Z`; backlog #0-60), and every `actions/checkout` sets `persist-credentials: false`. The repository setting `sha_pinning_required` is on (since 2026-09-29, after the #0-60 PR merged and `main`'s run was green), so a workflow with a tag-pinned `uses:` fails to start — current state in README "Infrastructure Hardening", how to resolve a SHA in ADR-0020 (`.ai/decisions/`).

Security scans (OWASP Dependency-Check, Snyk) run in separate workflows. The Snyk CLI is pinned by version and SHA-256 in `snyk.yml`'s `env` and the token is set only on the scan step (backlog #0-61); bump version and checksum together by hand, Renovate cannot. Unfixable CVEs are suppressed with a justification and expiry in `owasp-suppressions.xml` / `.snyk`; dependency version overrides for CVEs live in the root `pom.xml` properties with a comment naming the CVE.
