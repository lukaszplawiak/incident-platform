# Security context: tenant isolation and authentication

> Moved verbatim from `CLAUDE.md` on 2026-10-05 (CLAUDE.md is loaded into every session and every
> subagent, so it now keeps only a summary and points here). Edit the rules here, not there.

Read before changing anything that touches a tenant id, authentication, a security filter chain, an
HTTP client between services, a Kafka producer or consumer, a notification recipient, the platform
operator API, or tenant status. This is the property most easily broken in this system.

## Multi-tenancy invariants

Tenant isolation spans HTTP, Kafka and DB, and is the property most easily broken:

- HTTP: `JwtAuthFilter` sets `TenantContext` + MDC, and also stores the tenant as a request attribute (`TenantContext.REQUEST_ATTRIBUTE_TENANT_ID`) because the ThreadLocal is cleared before the observation filter finishes.
- Tenant id format: one, everywhere — a slug of 3-63 `[a-z0-9-]` (`TenantIds` in `shared`, backlog #0-92), checked where a tenant enters (a `CHECK` on every table with a `tenant_id`, in every service, token issue and read, the `X-Tenant-Id` header of auth-service's public endpoints, `TenantContext.set`, every Kafka record built and consumed). A tenant comes from authentication, travels in the data, and is never taken from a request body or an unsigned header.
- Kafka: the payload's `tenantId` is the record's tenant; the `X-Tenant-Id` header is a copy of it, written by one helper, `TenantRecords.forTenant`, which every sender uses (backlog #0-91). `TenantKafkaProducerInterceptor` only checks (metric, alert `KafkaRecordsWithoutTenant`) and writes nothing. Consumers must resolve tenant **per record** via `TenantKafkaRecordResolver` (the payload's valid tenant; the header must be there and equal it; otherwise `TenantResolutionException` → dead-letter, counted, alert `KafkaRecordsTenantRejected`) and clear `TenantContext` in a `finally` block. Never set tenant from a batch, nor a placeholder like `"unknown"` — `TenantKafkaConsumerInterceptor` is a validation layer only; a dead-letter record whose tenant could not be resolved carries none.
- Service-to-service HTTP: call with `ServiceTokenProvider.getToken(tenantId, ServiceNames.<TARGET>)` — the target's name, not your own. The token carries the tenant as a signed claim and `aud` names the one service that accepts it; `JwtAuthFilter` builds a `ServicePrincipal` from it and rejects it in any other service (fail closed: a filter built with no service name accepts none). auth-service accepts only `aud=auth-service`, and only its two `ROLE_SERVICE` endpoints use it (`/api/v1/internal/slack-workspace`, read by notification-service; `/api/v1/internal/tenant-status`, read by every other service, backlog #0-82) — a service reading auth-service-owned data goes through this narrow HTTP pull, not Kafka replication (backlog #0-21/#0-30). No filter reads `X-Tenant-Id` on HTTP, so a header alone authenticates nothing. A new HTTP client needs a connect/read timeout. `@AuthenticationPrincipal UserPrincipal` is `null` on a service call, so an endpoint open to `ROLE_SERVICE` must not dereference it. Fail-open client fallbacks must call `ClientFallbackMetrics.record` (backlog #0-11).
- The one tenant-less service token: a *purpose token* (`ServiceTokenProvider.getPurposeToken(TokenPurposes.API_KEY_INTROSPECTION, ServiceNames.AUTH_SERVICE)`, backlog #0-16), used by ingestion-service to ask auth-service which tenant an Integration API key belongs to before it knows the tenant. It becomes an `IntrospectionPrincipal` (no tenant), accepted only by a `JwtAuthFilter` built with that purpose and only on `POST /api/v1/internal/api-keys/introspect`; every other route denies it. The body carries the key's SHA-256, never the raw key. Don't add a second purpose without the same deny-by-default.
- Alert sources (incl. the platform's own Alertmanager) authenticate to ingestion-service with an Integration API key (only TENANT keys introspect as active; a PERSONAL key gets `active:false`), validated by that introspection with a 60 s cache: `401` = definite "no", `503` + `Retry-After` = could not check (Alertmanager retries 5xx, drops 4xx); `503` + `Retry-After: 300` + `TENANT_READ_ONLY` = the key is valid but its tenant is suspended read-only (alerts paused, not refused; backlog #0-82); a tenant suspended in full gets `403` + `TENANT_SUSPENDED`, not counted as a failed authentication of the sender's IP (backlog #0-82 step 2); a key in the 60 s cache is still caught by the status filter within 10 s. ingestion-service accepts no service tokens. Tenant ids `platform-operator` (the operator tenant that receives the platform's own alerts) and `system` are reserved (`ReservedTenants`).
- Notifications: tenant content (incident title, id, severity) goes only to members of that tenant. No platform-wide destination for it (no fallback address, no platform-wide Slack channel: since backlog #0-21 each tenant's Slack messages go only to its own workspace, with its own opt-in broadcast channel). When nobody in the tenant can be reached the entry becomes `UNDELIVERABLE` and the operator gets a content-free alert (identifiers and reason only). A channel's failure is recorded by a `NotificationFailureReason` (plus at most a checked provider code), never the provider's text, which only the log gets (backlog #0-93); a new channel maps its provider's failures the same way. Between teams of one tenant the default is also "no": `teamId` flows from `Incident` through every `IncidentEvent` (`shared`) and `NotificationQueueEntry`, and the PRIMARY on-call lookup is scoped to it via oncall-service's `/current?teamId=...` (backlog #0-12) — `null` for an incident with no team assignment falls back to tenant-wide, same as before #0-12.
- The one cross-tenant capability: tenant provisioning (backlog #0-80). An admin of `platform-operator` with a JWT, in a session that completed MFA within 12 h, with a factor whose MFA_ENABLED email was sent at least 24 h ago (#0-83: `auth_tokens.mfa_verified_at` + `users.mfa_enabled_notice_sent_at`, checked server-side per request from the token's `sessionId` by `MfaSessionStatusService`, no JWT claim; every MFA enable/disable emails the account through the auth email outbox), creates a customer tenant and invites its first admin through `/api/v1/platform/tenants` (auth-service, `TenantProvisioningService`); `PlatformAccess` refuses every other principal (customer admins, password-only sessions, API keys, service and purpose tokens) in the filter chain and on every method. Its writes are rate-limited per operator and in total, fail-closed (`PlatformRateLimiter`). It never acts inside a tenant once that tenant has an admin, with one exception: the MFA recovery of a customer tenant's only admin (#0-90, `MfaRecoveryService`, `/api/v1/platform/tenants/{id}/mfa-recovery`) — only while the tenant has no other active admin, the account emailed with a cancel link, the reset run by a scheduler only once the waiting period (default 72 h, 24 h to 7 days) has passed since that email was sent (factor, sessions, personal keys and the password), audited in both tenants. Keep it that narrow: a new operator action needs the same rule, audit in the operator tenant, and a backlog decision. Suspending and resuming a tenant (#0-82, next bullet) is the other such action: it changes the tenant's status, never data inside it; offboarding is #0-101. The operator tenant itself still bootstraps by invite (`OperatorTenantBootstrap`).
- Tenant status (backlog #0-82): a tenant is `ACTIVE`, `SUSPENDED` (mode `FULL` or `READ_ONLY`), `OFFBOARDING` or `OFFBOARDED` (the last two reserved for #0-101), owned by auth-service's `tenants` table and changed only by a platform operator (`/api/v1/platform/tenants/{id}/suspend`, `/resume`); a `SECURITY` reason requires `FULL` (400, and a CHECK in V30: read-only keeps an intruder's sessions and the account-security writes), and `platform-operator` itself cannot be suspended (it would lock the operators out of `/resume`). Every chain built by `buildCommonSecurity` carries `TenantStatusFilter` (`shared`), fed by a `TenantStatusProvider`: auth-service's `TenantAccessService`; in every service that sets `auth-service.base-url` (all the others) `AuthServiceTenantStatusProvider` (`shared`), which asks auth-service's `/api/v1/internal/tenant-status` and caches the answer 10 s (`tenant-status.cache.ttl`), one call per tenant at a time; when auth-service cannot answer, the last known status however old (static stability), and FULL only for a tenant never answered for (fail-open by decision); counted, alerts `TenantStatusLookupFailing` (outage, high) and `TenantStatusLookupRejected` (401/403 on the service token, a misconfiguration, critical at once). A service without that URL gets the "always FULL" default, so a new service must set it (CI: `.github/scripts/check-tenant-status-config.sh`). incident-service refuses a suspended tenant's STOMP `CONNECT` and closes its open sessions (`TenantWebSocketSessions`, a sweep that runs on every replica, deliberately without ShedLock); both use `TenantStatusProvider.knownAccessOf`, which never waits on auth-service — use it, not `accessOf`, on any thread that must not block. A public path with no principal that signs someone in (login, refresh, MFA, invite, reset) checks the tenant itself (`TenantAccessService.requireCanSignIn` / `requireCanJoin`), throwing `TenantSuspendedSignInException`, which `SignInRefusalHandler` audits and counts after the rollback (bounded per user: past `brute-force-protection.max-failures` refusals in its window, scope `SUSPENDED_SIGN_IN`, the answer is 429 with no event — a rolled-back refusal gives its invite or reset token back, so it could be repeated without end; its own scope, so a resumed tenant's users are not locked out of logging in); `requireCanWrite` is for a non-sign-in write. What a read-only tenant may still write is the service's `tenant-status.read-only.allowed-writes` (`"METHOD /ant/pattern"` entries on the MVC path; an entry without a write method fails startup; a `.`/`..` segment never matches): a new account-security route must be added there, and a route that also takes a non-security write (user status: reactivation) refuses that in its service. Every auth-service table holding a tenant's data has a foreign key to `tenants` (V31, not the two outboxes), so a new such table needs one too, with its name in `UnrecordedTenantHandler.TENANT_FOREIGN_KEYS` (`AuthRepositoryIntegrationTest` fails without either), and a fixture records its tenant first; a token naming a tenant without a row (only one minted outside auth-service, `/dev/token`) still gets full access (fail-open on purpose, a tripwire: counted, alert `PlatformTenantStatusRowMissing`). Only a `UserPrincipal` (a person's JWT or an API key) is checked; service tokens pass, so a person's action relayed with one checks the tenant itself (the Slack ACK path, `SlackActionService`). Background work is paused in the schedulers, not in the Kafka consumers, which go on writing rows (step 2b): notification-, escalation- and postmortem-service set `tenant-pause.table` (`<service>_paused_tenants`, equal to the constant their queries name, checked at startup), which `PausedTenantsSync` (`shared`, ShedLock, 10 s) fills from auth-service's own answer (`confirmedStateOf`: no pause or resumption on a fail-open guess) for the tenants with waiting work; every query that picks a tenant's work excludes that table (`NOT EXISTS`, never a skip in Java after the `LIMIT`: the paused tenant's oldest rows would starve the others) and checks `TenantWorkGuard` per row; resumption runs the service's `PausableWork.onResume` in the same transaction (escalation timers move on by the pause). A pause is measured from the suspension's own time (`since` = `suspended_at` in auth-service's answer), never from when a service noticed it. A new scheduler that acts for a tenant needs all three, and, as the guard may wait on auth-service (about 3 s per uncached tenant in an outage), a processing budget shorter than its ShedLock, checked at startup and started before it calls `TenantWorkGuard.prefetch` with its batch's tenants (looked up in parallel before the loop, so the per-row check reads the cache; the prefetch then counts against the budget, not against the margin left below the lock). Notification, escalation and postmortem do all of this. Suspension revokes nothing (resumed, a tenant works as before) but a `FULL` one ends the tenant's sessions at once. A `READ_ONLY` tenant's alerts get 503 + `Retry-After` from ingestion-service (introspection answers `paused:true`, a success for its circuit breaker; and ingestion-service sets `tenant-status.read-only.retry-after`, so its `TenantStatusFilter` answers a read-only write 503 too, never a 4xx), so Alertmanager keeps and retries them; `FULL` gets 403 `TENANT_SUSPENDED` (introspection `suspended:true`), not counted against the sender IP's failed-authentication limit. In auth-service a lost lock (`PessimisticLockingFailureException`: lock timeout, deadlock) is 503 + `Retry-After` (`TenantStatusBusyHandler`). A "deactivated" user is the same idea per person: no refresh, no personal API key, sessions ended.
- Async: propagate with `TenantAwareTaskDecorator`; don't hand work to a plain executor.
- Queries are always tenant-scoped; `@PreAuthorize`/filter-chain rules use the non-prefixed `hasRole("ADMIN")` form (`SecurityRoles.*_NAME`), while JWT claims and `UserPrincipal.hasRole` use the `ROLE_`-prefixed constants.
